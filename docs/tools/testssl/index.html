This tool sends traffic to the systems you point it at. Use it only on infrastructure you own or have explicit written permission to test. The examples use private documentation ranges and placeholder names.

Overview

testssl.sh is a command-line TLS assessment script. It checks supported protocols, cipher suites, certificate details, forward secrecy, HTTP security headers and a selection of known TLS vulnerabilities. It is broader than a single OpenSSL handshake and produces human-readable or machine-readable reports.

The installer's tls group installs OpenSSL and ensures testssl.sh is available. It prefers a native package when the distribution has one and falls back to a shallow clone of the upstream Git repository at /opt/testssl.sh, linked as /usr/local/bin/testssl.sh.

What it does

  • Enumerate supported TLS and SSL protocol versions.
  • List cipher suites by protocol and strength.
  • Inspect certificate chain, validity, names and key details.
  • Check forward secrecy, HSTS and selected HTTP headers.
  • Test for known TLS issues such as Heartbleed, CCS injection and ROBOT.
  • Produce plain text, JSON, CSV or HTML output.

Good for

  • A repeatable TLS configuration baseline for a lab endpoint.
  • Finding obsolete protocol versions or weak ciphers.
  • Checking certificate names, dates and chain issues.
  • Producing a report to compare before and after a configuration change.

Limits

  • It is active and can be slow; a full run sends many probes.
  • Results depend on the version and its test definitions; TLS best practice changes.
  • It does not replace a full application or vulnerability assessment.
  • Some checks depend on HTTP behavior and may not apply to non-HTTP services.
  • A poor rating is a prompt to investigate, not proof of exploitability.

How the installer handles it

The tls group installs OpenSSL, then calls the testssl.sh handler. The handler first tries the native package (testssl.sh on apt/pacman/apk, testssl on dnf/brew). If the command is still missing, it clones the upstream repository and creates a symlink.

On the audited Ubuntu 26.04 system, the native testssl.sh package was installed (version 3.2.2) and the command was available as testssl. The installer's check accepts either testssl.sh or testssl.

The installer's tls group is considered complete only when these commands exist: openssl, testssl.sh.

Install just this group

sudo eergn-recon-installer --tool tls

From a downloaded standalone script, use sudo ./eergn-recon-installer.sh --tool tls. To install every group without the menu, use sudo eergn-recon-installer --all.

Installation

Install the TLS group

Installs OpenSSL and ensures testssl.sh is available through a package or the Git fallback.

sudo eergn-recon-installer --tool tls

Manual Git fallback

Use this only if the installer's fallback did not run or you need to repair it.

sudo git clone --depth 1 https://github.com/testssl/testssl.sh.git /opt/testssl.sh
sudo ln -sf /opt/testssl.sh/testssl.sh /usr/local/bin/testssl.sh

Verify

testssl.sh --version
testssl --version
openssl version
eergn-recon-installer --check
Verification is not a functional test

A version banner only proves the binary is on PATH. Run the smallest safe command against a lab endpoint to confirm the tool works in your environment.

Basic usage

Run the standard checks

The quiet flag reduces progress output. A full run can take a minute or more.

testssl --quiet lab.example.internal:443

Check protocols only

A focused check is faster and easier to compare.

testssl --protocols lab.example.internal:443

Check certificate and headers

Useful for a quick certificate and HTTP security-header review.

testssl --server-defaults --headers lab.example.internal:443

Examples for an authorized lab

Baseline a lab endpoint

Run the standard checks and keep both text and JSON output.

testssl --quiet --jsonfile tls-baseline.json lab.example.internal:443 | tee tls-baseline.txt

Record the testssl version with the result; ratings and checks change between releases.

Check only protocols

Compare supported protocol versions before and after a change.

testssl --quiet --protocols lab.example.internal:443

This is much faster than a full run and still shows obsolete protocol support.

Test a STARTTLS service

Assess SMTP, IMAP, POP3 or another upgrade-capable service.

testssl --quiet --starttls smtp lab-mail.example.internal:25

Use only a service in scope and confirm the port actually supports STARTTLS.

Understanding the output

A full run prints one line per finding group. The excerpt below is illustrative; ratings and findings depend on the endpoint and testssl version.

Testing protocols via sockets
 SSLv2      not offered
 SSLv3      not offered
 TLS 1.2    offered (OK)
 TLS 1.3    offered (OK)
 Testing cipher categories
 NULL ciphers             not offered
 Forward Secrecy          offered (OK)
 Testing server defaults
 Certificate               matches supplied hostname
 Common Name (CN)          lab.example.internal
 Issuer                    Lab Internal CA
 Valid until               2027-01-01
 Overall Grade             A
  • The overall grade summarizes many checks; read the individual findings before acting.
  • A certificate that does not match the name is a configuration problem even if the grade is high.
  • Some checks are informational rather than failures.
  • Store the testssl version, target, port and date with every report.

Advanced usage

For repeatable baselines, pin the testssl version, use the same option set, and store JSON. Use --starttls for non-HTTP services and --headers only for HTTP endpoints. Mass-testing options can scan many hosts, but they multiply traffic; keep them inside the authorized scope and a defined time window.

Troubleshooting

SymptomLikely causeWhat to try
testssl.sh: command not foundThe group is incomplete or the symlink was not created.Check /opt/testssl.sh, rerun the group, or create the symlink manually.
The run is very slowA full scan performs many sequential probes.Use focused options such as --protocols or increase the connect timeout.
Certificate name mismatchThe endpoint serves a certificate for another name or SNI is missing.Use the correct hostname and compare with OpenSSL s_client.
STARTTLS check failsThe service does not support STARTTLS on that port.Confirm with the service's own documentation; do not assume TLS is required.
Inconsistent results between runsLoad balancers, different backends or changed configuration.Record the time and compare multiple runs; check whether the endpoint is load-balanced.

Security and etiquette

  • Use only against endpoints in scope; a full run is noisy and slow.
  • Do not run mass-testing modes outside a defined window and target list.
  • Do not treat a grade as a complete security assessment.
  • Protect reports; they can reveal internal names, certificates and configuration.
  • Keep testssl and OpenSSL current, because checks and defaults change.
