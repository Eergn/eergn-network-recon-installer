This tool sends traffic to the systems you point it at. Use it only on infrastructure you own or have explicit written permission to test. The examples use private documentation ranges and placeholder names.

Overview

dig is the DNS lookup utility from the BIND project. It sends a query to a resolver and prints the question, answer, authority and additional sections. Unlike a browser lookup, it lets you choose the record type, server, transport and flags.

The installer groups dig and whois under the dns group. The group is only complete when both commands exist. On Debian/Ubuntu the apt mapping requests dnsutils and whois; newer Ubuntu releases may provide dig through bind9-dnsutils instead, which is an important compatibility detail.

What it does

  • Query A, AAAA, CNAME, MX, NS, SOA, TXT, SRV, CAA and other record types.
  • Choose the resolver with @server.
  • Show short answers or full protocol sections.
  • Trace the delegation chain from the root with +trace.
  • Request DNSSEC records and inspect the AD flag.
  • Use TCP or a specific source address and port.

Good for

  • Checking which addresses and mail servers a name publishes.
  • Comparing answers from different resolvers.
  • Verifying SPF, DMARC and other TXT records.
  • Tracing where a delegation breaks.
  • Producing short answer lists for scripts.

Limits

  • It reads DNS data; it does not prove that a service is reachable.
  • Cached answers can be stale or differ by resolver.
  • The absence of a record in one query does not prove it does not exist elsewhere.
  • Zone transfers usually require authorization and are often refused.
  • DNSSEC validation depends on the resolver and the +dnssec request, not on dig alone.

How the installer handles it

The dns group installs the DNS client package and whois, then checks for both dig and whois. On the audited Ubuntu 26.04 system, the apt mapping's dnsutils had no installation candidate; bind9-dnsutils provided dig. This means the group can require a manual package adjustment on newer Ubuntu releases.

The installer's dns group is considered complete only when these commands exist: dig, whois.

Install just this group

sudo eergn-recon-installer --tool dns

From a downloaded standalone script, use sudo ./eergn-recon-installer.sh --tool dns. To install every group without the menu, use sudo eergn-recon-installer --all.

Installation

Install the DNS group

Installs the mapped DNS package and whois, then checks both commands.

sudo eergn-recon-installer --tool dns

Ubuntu fallback if dnsutils is unavailable

Use this when APT cannot find dnsutils. It provides dig on newer Ubuntu releases.

sudo apt install bind9-dnsutils whois

Verify

dig -v
whois --version
eergn-recon-installer --check
Verification is not a functional test

A version banner only proves the binary is on PATH. Run the smallest safe command against a lab endpoint to confirm the tool works in your environment.

Basic usage

Look up an address record

The short form prints only the answer data, which is convenient for scripts.

dig example.com A +short

Query a specific resolver

Useful for comparing the local resolver with an authoritative or public resolver.

dig @192.168.1.53 example.com A

Fetch several record types

Run each type separately; ANY is often minimized or refused.

dig example.com MX
dig example.com TXT
dig example.com NS

Examples for an authorized lab

Check common records

Collect the address, mail, name-server and TXT records for a lab domain.

for type in A AAAA MX NS TXT; do
  echo "== $type =="
  dig example.com "$type" +noall +answer
done

Use a domain you own or are authorized to query. The output shows record data, not service health.

Compare resolvers

Ask the local resolver and an authoritative server the same question.

dig @192.168.1.53 example.com A +noall +answer
dig @198.51.100.53 example.com A +noall +answer

Different answers can indicate caching, split-horizon DNS or a delegation problem.

Reverse lookup

Map an address back to a name when a PTR record exists.

dig -x 192.0.2.10 +short

Private ranges often have no PTR records; an empty answer is normal.

Understanding the output

A normal query prints header, question, answer, authority and additional sections. The values below are illustrative.

;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 12345
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1

;; QUESTION SECTION:
;example.com.                   IN      A

;; ANSWER SECTION:
example.com.            300     IN      A       192.0.2.10

;; Query time: 12 msec
;; SERVER: 192.168.1.53#53(192.168.1.53) (UDP)
  • status reports the DNS response code, such as NOERROR, NXDOMAIN, SERVFAIL or REFUSED.
  • flags include qr, rd, ra and, when validated, ad.
  • The TTL is the remaining cache time, not the record's configured lifetime.
  • The SERVER line shows which resolver actually answered.

Advanced usage

+trace performs iterative queries from the root and is useful for understanding delegation, but it can be slow and may be blocked. For DNSSEC, request +dnssec and inspect the ad flag from a validating resolver; dig itself is not a validator. For zone transfers, use AXFR only with explicit authorization, and expect refusal on most servers.

Troubleshooting

SymptomLikely causeWhat to try
dig: command not foundThe DNS group is incomplete or the package name changed.Install bind9-dnsutils on newer Ubuntu, or the distribution's DNS client package.
status: SERVFAILThe resolver could not complete the query, often due to DNSSEC or upstream failure.Try another resolver and check the delegation with +trace.
status: REFUSEDThe server does not allow queries from this client or for this zone.Use an authorized resolver or ask the DNS owner.
Query times outUDP is blocked, the server is unreachable, or the port is wrong.Try +tcp, verify the resolver address, and set a short +time.
Empty answer for a name that works in a browserThe browser may use a different resolver or search domain.Query the same resolver explicitly and try the fully qualified name with a trailing dot.

Security and etiquette

  • Query only domains you own or are authorized to investigate.
  • DNS queries are visible to resolvers and network monitoring.
  • Do not attempt zone transfers without written authorization.
  • Treat internal DNS data as sensitive topology information.
  • Prefer encrypted DNS only where policy permits it; local resolvers may be required for split-horizon names.
