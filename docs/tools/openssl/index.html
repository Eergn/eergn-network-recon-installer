OpenSSL s_client

A precise TLS client for one handshake at a time: certificate chains, protocol versions, SNI, STARTTLS and verification results.

This tool sends traffic to the systems you point it at. Use it only on infrastructure you own or have explicit written permission to test. The examples use private documentation ranges and placeholder names.

Overview

OpenSSL is a cryptography toolkit. The s_client command opens a TLS connection and prints handshake and certificate details. It is the low-level counterpart to testssl.sh: one endpoint, one handshake, full control over SNI, protocol version, CA trust and STARTTLS.

OpenSSL is part of the installer's tls group. The group also requires testssl.sh, which is installed through a native package when available or cloned from upstream as a fallback.

What it does

  • Open a TLS connection to a host and port.
  • Print the peer certificate chain and verification result.
  • Set SNI explicitly with -servername.
  • Select a specific TLS protocol version for testing.
  • Use STARTTLS for mail, LDAP and other upgrade protocols.
  • Print a brief handshake summary or detailed state.

Good for

  • Inspecting the certificate a server presents for a specific name.
  • Checking whether a server supports TLS 1.2 or TLS 1.3.
  • Testing STARTTLS on a mail or directory service.
  • Capturing a certificate for offline inspection.

Limits

  • It tests one connection with the options you choose; it is not a configuration scanner.
  • A successful handshake does not mean the application behind it is healthy.
  • Verification depends on the trust store and the name you pass.
  • Protocol-specific failures can be caused by the client's own cipher or provider configuration.
  • It does not test every cipher, vulnerability or client compatibility profile.

How the installer handles it

The tls group installs OpenSSL, ensures testssl.sh is available, and checks for both openssl and testssl.sh. On macOS the mapping requests openssl@3; the system LibreSSL binary may take precedence depending on PATH.

testssl.sh is handled separately: the installer uses a native package if one exists, otherwise it clones the upstream repository to /opt/testssl.sh and links /usr/local/bin/testssl.sh.

The installer's tls group is considered complete only when these commands exist: openssl, testssl.sh.

Install just this group

sudo eergn-recon-installer --tool tls

From a downloaded standalone script, use sudo ./eergn-recon-installer.sh --tool tls. To install every group without the menu, use sudo eergn-recon-installer --all.

Installation

Install the TLS group

Installs OpenSSL and ensures testssl.sh is available.

sudo eergn-recon-installer --tool tls

Verify

openssl version
testssl.sh --version
eergn-recon-installer --check
Verification is not a functional test

A version banner only proves the binary is on PATH. Run the smallest safe command against a lab endpoint to confirm the tool works in your environment.

Basic usage

Inspect the default certificate

Always set SNI when testing a virtual host. Redirecting stdin prevents s_client from waiting for input.

openssl s_client -connect lab.example.internal:443 -servername lab.example.internal < /dev/null

Print a brief summary

The brief form reduces output but still requires a readable connection.

openssl s_client -connect lab.example.internal:443 -servername lab.example.internal -brief < /dev/null

Verify the chain and name

A failure here means the presented chain or name did not validate against the local trust store.

openssl s_client -connect lab.example.internal:443 -servername lab.example.internal -verify_return_error -verify_hostname lab.example.internal < /dev/null

These are the options most useful for the workflows in this documentation. Run openssl s_client -help for the complete list supported by your installed version.

Examples for an authorized lab

Save the peer certificate

Capture the certificate chain for offline inspection.

openssl s_client -connect lab.example.internal:443 -servername lab.example.internal -showcerts < /dev/null > handshake.txt 2>&1

The file contains more than the certificate. Extract the PEM block before feeding it to other tools.

Check a specific protocol

Fail quickly if the server does not negotiate the requested version.

openssl s_client -connect lab.example.internal:443 -servername lab.example.internal -tls1_3 -brief < /dev/null

Repeat with -tls1_2 to compare. Do not enable obsolete protocols just to make a test pass.

Test SMTP STARTTLS

Upgrade a mail connection before the handshake.

openssl s_client -starttls smtp -connect 192.168.1.25:25 -servername mail.example.internal < /dev/null

The server must support STARTTLS on that port; otherwise the upgrade fails before TLS begins.

Understanding the output

A successful handshake prints protocol, cipher, session and certificate details. The example is abbreviated and illustrative.

CONNECTED(00000003)
depth=0 CN = lab.example.internal
verify return:1
---
Certificate chain
 0 s:CN = lab.example.internal
   i:CN = Lab Internal CA
---
New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384
Server public key is 256 bit
Secure Renegotiation IS supported
SSL-Session:
    Protocol  : TLSv1.3
    Cipher    : TLS_AES_256_GCM_SHA384
---
Verify return code: 0 (ok)
  • Verify return code: 0 (ok) means the chain validated against the trust store for the checks performed.
  • The subject and issuer lines show the leaf and its issuer; use -showcerts for the full chain.
  • The protocol and cipher show what this specific handshake negotiated, not everything the server supports.
  • SNI matters: connecting by IP without -servername can return a different certificate.

Advanced usage

To inspect the leaf certificate in detail, extract the PEM block from -showcerts output and run openssl x509 -noout -subject -issuer -dates -ext subjectAltName. To compare trust stores, pass -CAfile explicitly instead of relying on the system default. For a broad configuration review, use testssl.sh; s_client is best for a controlled, single handshake.

Troubleshooting

SymptomLikely causeWhat to try
no peer certificate availableThe endpoint is not speaking TLS on that port, or the handshake failed before the certificate.Confirm the port and protocol, and try -state for more detail.
Verification fails with a self-signed certificateThe issuer is not in the local trust store.Import the lab CA only if it is trusted for this environment; do not disable verification as a habit.
Wrong certificate returnedSNI is missing or the name does not match the virtual host.Add -servername and -verify_hostname with the exact DNS name.
Handshake fails for one protocol versionThe server does not support that version or the client's provider disables it.Confirm with testssl.sh before concluding the server is misconfigured.
Command appears to hangs_client is waiting for stdin.Redirect < /dev/null or use -quiet with an explicit timeout.

Security and etiquette

  • Test only endpoints in scope; TLS handshakes are logged by servers and middleboxes.
  • Do not disable certificate verification to make a test pass.
  • Do not enable obsolete protocols or weak ciphers outside an isolated lab.
  • Private keys captured during testing must be protected or destroyed.
  • Use testssl.sh for broad checks and s_client for targeted inspection.
