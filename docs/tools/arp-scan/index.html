arp-scan

Layer-2 host discovery for the local broadcast domain, using ARP requests to map IPv4 addresses to MAC addresses and vendors.

This tool sends traffic to the systems you point it at. Use it only on infrastructure you own or have explicit written permission to test. The examples use private documentation ranges and placeholder names.

Overview

arp-scan sends ARP requests to IPv4 addresses on the local link and records the replies. Because ARP is required for local IPv4 communication and is not routed, it often finds hosts that ignore ICMP or block higher-layer probes.

The installer's arp-scan group installs the tool and checks for the arp-scan command. It is most useful as the first pass on a lab segment before ICMP or port-based discovery.

What it does

  • Discover hosts on the local broadcast domain with ARP.
  • Report IPv4 address, MAC address and, when the vendor database is available, the hardware vendor.
  • Accept CIDR, ranges, network:mask and host lists as targets.
  • Support custom output formats for parsing.
  • Read targets from a file or generate them from an interface's local network.

Good for

  • Inventorying a lab segment where ICMP is filtered.
  • Spotting unexpected devices by MAC vendor.
  • Confirming which interface and subnet a host is actually on.
  • Producing a simple IP-to-MAC table for asset reconciliation.

Limits

  • ARP does not cross routers; it only sees the local broadcast domain.
  • Wireless client isolation, bridge filtering and some virtual switches can suppress replies.
  • It discovers IPv4 hosts, not open ports or services.
  • A missing reply does not always mean the host is absent; the device may ignore or filter ARP.
  • Vendor lookup depends on the local MAC vendor database and can be incomplete or wrong.

How the installer handles it

The arp-scan group installs the distribution package and checks for the arp-scan command. On the RHEL family, the installer warns that EPEL may be required.

The tool uses raw sockets. On Linux it may be capability-aware, but the packaged binary and local permissions determine whether sudo is needed. The installer does not change capabilities or setuid bits.

The installer's arp-scan group is considered complete only when these commands exist: arp-scan.

Install just this group

sudo eergn-recon-installer --tool arp-scan

From a downloaded standalone script, use sudo ./eergn-recon-installer.sh --tool arp-scan. To install every group without the menu, use sudo eergn-recon-installer --all.

Installation

Install the group

Installs arp-scan. Run the tool itself with enough privilege for raw sockets.

sudo eergn-recon-installer --tool arp-scan

Verify

arp-scan --version
arp-scan --help | head
eergn-recon-installer --check
Verification is not a functional test

A version banner only proves the binary is on PATH. Run the smallest safe command against a lab endpoint to confirm the tool works in your environment.

Basic usage

Scan the local network on an interface

Replace eth0 with the lab interface. --localnet derives targets from that interface's address and netmask.

sudo arp-scan --interface=eth0 --localnet

Scan an explicit subnet

Use a CIDR inside the local broadcast domain. Routed subnets will not receive ARP requests.

sudo arp-scan --interface=eth0 192.168.1.0/24

Produce a parseable table

Useful for logs and comparison. MAC vendor data still depends on the local database.

sudo arp-scan --interface=eth0 --localnet --plain --ignoredups

Examples for an authorized lab

Find devices and vendors

Scan the lab segment and keep a plain, duplicate-free table.

sudo arp-scan -I eth0 -l -x -g 2>/dev/null | tee arp-scan-$(date +%F).txt

The header is suppressed by -x; record the interface and time separately if you need provenance.

Target a small range

Limit the scan to a specific address range inside the local link.

sudo arp-scan -I eth0 192.168.1.10-192.168.1.40

Ranges are inclusive. Always confirm the range is in scope.

Resolve hostnames

Add reverse DNS for responding addresses when a resolver is available.

sudo arp-scan -I eth0 -l -d

Reverse DNS can be slow and may leak the scan to internal resolvers.

Understanding the output

The default output is a table with interface information, responding hosts and a summary. Addresses and vendors below are illustrative.

Interface: eth0, type: EN10MB, MAC: 02:00:00:00:00:01, IPv4: 192.168.1.10
Starting arp-scan 1.10.0 with 256 hosts (https://github.com/royhills/arp-scan)
192.168.1.1     02:00:00:00:00:02       Example Networks
192.168.1.20    02:00:00:00:00:14       Example Devices

2 packets received by filter, 0 packets dropped by kernel
Ending arp-scan 1.10.0: 256 hosts scanned in 2.015 seconds (127.05 hosts/sec). 2 responded
  • Only hosts that answered ARP appear. Absence is not proof that a host is offline.
  • The MAC vendor column comes from the local vendor database and can be blank or inaccurate.
  • The summary shows scan rate and response count; record it with the output.
  • Use --plain and --ignoredups when the output will be parsed.

Advanced usage

For repeatable inventories, pin the interface, disable name resolution unless it is needed, and store the exact command with the output. A custom format such as --format='${ip}\t${mac}\t${vendor}' is easier to compare than the decorated default. If a managed switch or wireless controller has client isolation enabled, coordinate with its owner before concluding that hosts are absent.

Troubleshooting

SymptomLikely causeWhat to try
Could not open a raw socketThe process lacks raw-socket privilege.Run with sudo, or grant the appropriate capability according to local policy.
No hosts respondWrong interface, wrong subnet, client isolation or a virtual network that does not pass ARP.Confirm the interface address with ip addr and test from another host on the same segment.
Vendor column is blankThe MAC vendor database is missing or the prefix is unregistered.Update the package's vendor data if available; do not treat a blank vendor as an error.
Scan is very slowLarge range, retries or a high timeout.Reduce the range, lower retries/timeouts, or use --bandwidth on constrained links.

Security and etiquette

  • ARP scanning only reaches the local broadcast domain; keep it inside the authorized segment.
  • Do not run it on networks where you lack permission, even if the range is private.
  • Wireless and virtual segments may carry other users' traffic; coordinate with the network owner.
  • MAC and vendor data can identify personal devices; handle it as sensitive inventory data.
  • Rate-limit large scans to avoid disrupting fragile lab equipment.
