MTR

Combined traceroute and ping: follow a path hop by hop while measuring loss and latency, with report, JSON, XML and CSV output.

This tool sends traffic to the systems you point it at. Use it only on infrastructure you own or have explicit written permission to test. The examples use private documentation ranges and placeholder names.

Overview

MTR combines traceroute and ping. It discovers the path to a target and continuously probes each hop, showing packet loss and round-trip latency per hop. It is the fastest way to tell whether a problem is local, on the path, or at the destination.

The installer's mtr group installs mtr-tiny on Debian/Ubuntu and the distribution's MTR package elsewhere, then checks for the mtr command. The tiny package omits the GTK interface, which is appropriate for servers.

What it does

  • Discover the layer-3 path to a target.
  • Continuously measure loss and latency at each hop.
  • Use ICMP, UDP or TCP probes to work around filtering.
  • Render an interactive terminal view or a static report.
  • Export JSON, XML or CSV for later analysis.

Good for

  • Locating where latency or loss begins on a path.
  • Comparing a direct path with a VPN or overlay path.
  • Producing evidence for a network owner when a link degrades.
  • Testing whether a filtered target responds to TCP but not ICMP.

Limits

  • It measures the path from this host at this moment, not a historical baseline.
  • ICMP rate limiting can make later hops appear lossy even when the path is healthy.
  • Routers may not respond to the probe type, so blank hops are common.
  • The default ICMP mode often needs root.
  • A TCP probe to one port does not represent all application traffic.

How the installer handles it

The mtr group installs mtr-tiny on Debian/Ubuntu and mtr on the other mapped package managers. It checks for the mtr command.

The installer does not grant raw-socket capabilities. On the audited Ubuntu system, /usr/bin/mtr had no file capabilities, so the default ICMP mode was expected to need sudo.

The installer's mtr group is considered complete only when these commands exist: mtr.

Install just this group

sudo eergn-recon-installer --tool mtr

From a downloaded standalone script, use sudo ./eergn-recon-installer.sh --tool mtr. To install every group without the menu, use sudo eergn-recon-installer --all.

Installation

Install the group

Installs the distribution package and verifies mtr.

sudo eergn-recon-installer --tool mtr

Verify

mtr --version
mtr --help | head
eergn-recon-installer --check
Verification is not a functional test

A version banner only proves the binary is on PATH. Run the smallest safe command against a lab endpoint to confirm the tool works in your environment.

Basic usage

Static report

-r report mode, -w wide output, -c 20 cycles. This is the form to save with an incident.

mtr -rw -c 20 192.168.1.1

Use TCP to a specific port

TCP mode often works when ICMP is filtered. It probes only the path to that port.

mtr -T -P 443 -rw -c 10 lab.example.internal

Machine-readable output

JSON is easier to store and compare than the interactive view.

mtr -j -c 10 192.168.1.1

Examples for an authorized lab

Save a path report

Capture a fixed number of cycles in a file for later comparison.

mtr -rw -c 30 -n 192.168.1.1 | tee mtr-gateway-$(date +%F-%H%M).txt

Use -n for speed or omit it to see names. Record the time and source host.

Test a filtered web host over TCP

Probe the path to port 443 when ICMP is blocked.

mtr -T -P 443 -rw -c 15 -n lab.example.internal

A successful TCP path does not prove the application is healthy.

Export JSON for comparison

Keep structured data with a run label.

mtr -j -c 10 -n 192.168.1.1 > mtr-192.168.1.1.json

JSON schemas can vary by MTR version; store the version with the file.

Understanding the output

Report mode prints one row per hop. The values below are illustrative and truncated.

Start: 2026-01-01T12:00:00+0000
HOST: lab-client                    Loss%   Snt   Last   Avg  Best  Wrst StDev
  1.|-- 192.168.1.1                  0.0%    20    0.4   0.4   0.3   0.6   0.1
  2.|-- 192.0.2.1                    0.0%    20    1.8   2.1   1.5   3.0   0.4
  3.|-- 198.51.100.10                0.0%    20    8.4   8.9   8.1  10.2   0.6
  4.|-- 203.0.113.20                 0.0%    20    9.1   9.4   8.8  11.0   0.7
  • Loss% at intermediate hops can be an artifact of control-plane rate limiting; loss at the final hop is more meaningful.
  • Avg and StDev show latency and jitter. A rising average along the path localizes added delay.
  • Blank or ??? hops did not answer that probe type, which is not necessarily a fault.
  • Save the command, cycle count, probe type and time with the report.

Advanced usage

Use -T or -u when ICMP is filtered, and always record the probe type because different types can produce different paths. For comparisons, keep the cycle count, source host, target name and timestamp constant. Very long runs are rarely useful; a few dozen cycles are usually enough to distinguish persistent loss from a transient blip.

Troubleshooting

SymptomLikely causeWhat to try
mtr: Permission deniedICMP raw sockets require privilege on this build.Run the report with sudo, or use -T if local policy permits unprivileged TCP probes.
Loss at every hop but the target is fineICMP responses from routers are rate-limited or deprioritized.Focus on the final hop and compare with TCP mode or application measurements.
All hops show ???The network blocks the probe type or the target is unreachable.Try -T -P 443 or another in-scope port, and confirm routing.
Names are slowReverse DNS is timing out for many hops.Add -n for numeric output.

Security and etiquette

  • Use MTR only against targets in scope; it sends repeated probes and is visible.
  • Prefer the smallest cycle count that answers the question.
  • Do not use TCP mode to probe arbitrary ports outside the agreed scope.
  • Stored path data reveals internal addresses and topology.
  • Coordinate long-running tests with the network owner.
