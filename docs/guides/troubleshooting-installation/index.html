Troubleshooting installation

A structured diagnostic path for the installer and its APT repository. Start with the exact error, confirm the package manager, and avoid destructive permission changes.

Purpose

Resolve installation failures without guessing. The installer writes package-manager output to a temporary log and reports failed package names. Those two pieces of evidence are usually enough to identify the layer that failed: repository, network, package availability, dependency or privilege.

First diagnostics

# What is installed and where did it come from?
command -v eergn-recon-installer
eergn-recon-installer --version
eergn-recon-installer --check

# Package state on Debian-based systems
dpkg -s eergn-recon-installer

# Installed tool paths
for c in nmap ncat nc arp-scan fping mtr dig whois openssl testssl.sh iperf3 iftop nethogs; do
  printf '%-12s %s\n' "$c" "$(command -v "$c" || echo missing)"
done

Use --check before reinstalling. It distinguishes "package command missing" from "tool command missing" and exits non-zero when anything is absent. The installer needs root or sudo to install packages; --check does not.

APT repository problems

SymptomLikely causeDiagnostic and fix
E: Unable to locate package eergn-recon-installerSource not added, wrong suite, or apt update not runCheck /etc/apt/sources.list.d/eergn.list and run sudo apt update
NO_PUBKEY / signature verification failedKeyring missing, wrong path, or repository changed keyConfirm the key file exists and the signed-by path matches
404 Not Found from GitHub PagesWrong URL, repository not deployed, or path typoFetch the Release file with curl -I and check the site URL
Temporary failure resolving ...DNS or network problemResolve the hostname, test HTTPS connectivity, check proxy configuration
Release file ... is not valid yetClock skewCorrect the system clock; signature dates are checked
Hash Sum mismatchProxy/cache corruption or an inconsistent repositoryRetry after sudo apt clean; avoid deleting random files

For signature problems, verify the published fingerprint before trusting a newly fetched key:

gpg --show-keys /usr/share/keyrings/eergn-archive-keyring.gpg
# Expected fingerprint: 900D437EB8F512053DA25632AEF17B55E71A8350

If the file is missing or the fingerprint differs, re-fetch it deliberately and investigate before adding it. Do not disable signature checks to make the error disappear.

Package manager and platform problems

SymptomLikely causeFix
No supported package manager foundUnsupported distribution or minimal containerInstall a supported base system or use a distribution with apt, dnf, yum, pacman, zypper, apk or Homebrew
Root privileges requiredNot root and sudo is unavailableRun as root or install/configure sudo; do not blindly change ownership of system files
Homebrew must not be run as rootmacOS run with sudoRun without sudo; Homebrew manages its own prefixes
Homebrew is required on macOSbrew not on PATHInstall Homebrew and ensure its shell environment is loaded
arp-scan, iftop, nethogs fail on RHEL familyPackages are in EPELInstall epel-release, then re-run the installer
nethogs fails on macOSLinux-focused toolExpected; the installer reports the failure and continues

The installer does not stop when one package fails. It continues with the remaining groups and prints the failed package names at the end. Use that list rather than re-running every group blindly.

testssl.sh problems

The installer first tries a native package: testssl.sh on apt/pacman/apk and testssl on dnf/brew. If that fails and the package manager is not Homebrew, it falls back to cloning https://github.com/testssl/testssl.sh into /opt/testssl.sh and linking /usr/local/bin/testssl.sh.

SymptomWhat to check
testssl.sh: command not foundNative package and Git fallback both failed; inspect the log and confirm Git is available
/opt/testssl.sh exists but command missingSymlink missing or /usr/local/bin not on PATH; inspect with ls -l /usr/local/bin/testssl.sh
Git clone failsNo network, Git missing, proxy restriction or no permission under /opt
Native package installs testssl insteadThe installer accepts either command name; verify with command -v testssl

PATH problems

If a command exists but the installer cannot see it, check the shell's PATH. Some distributions install network tools in /usr/sbin; non-root users may not have that directory in PATH depending on the system configuration.

printf '%s\n' "$PATH" | tr ':' '\n'
ls -l /usr/sbin/arp-scan /usr/sbin/iftop /usr/sbin/nethogs 2>/dev/null

Prefer fixing PATH or invoking the absolute path over copying binaries into directories. Do not recursively change permissions on /usr, /opt or /usr/local.

Reading the installer log

The installer prints Log file: /tmp/Eergn-installer.XXXXXX at the start. If a package fails, it prints the failed names and the log path again. Read the tail of the log for the package manager's exact error:

tail -n 80 /tmp/Eergn-installer.XXXXXX

The log path is temporary. Copy it into your engagement or support notes before rebooting or cleaning /tmp.

Installer behavior that can surprise you

  • --dry-run prints simulated ok lines. It does not prove installation.
  • A group is skipped if all of its required commands already exist. Use --force to reinstall.
  • --check requires every command in all groups, so a partial install exits non-zero.
  • On a non-interactive shell with no arguments, the installer installs everything.
  • It does not add repositories for every tool; on RHEL-family systems, EPEL may be required first.

When to stop and ask

Stop if a fix would disable signature verification, loosen permissions broadly, add an untrusted repository, or run an unknown script as root. Those are security decisions, not installation steps. Open an issue with the exact command, distribution, installer version and the relevant log lines, after removing secrets and internal addresses.
