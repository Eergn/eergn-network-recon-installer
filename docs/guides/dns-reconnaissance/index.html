DNS reconnaissance

Read the records a domain publishes, inspect reverse DNS, trace delegation and collect registration data. DNS queries are generally lightweight, but they are still traffic to third-party infrastructure.

Purpose

Collect the public DNS and registration facts for a domain you are authorized to assess. This is usually a low-impact starting point, but it can reveal internal naming, mail providers, third-party services and ownership clues.

Prerequisites

  • Installed group dns (dig and whois).
  • Authorization to query the domain and its authoritative servers. Public DNS is public, but bulk enumeration is not automatically acceptable.
  • A resolver you trust, or the authoritative server address when you need an authoritative answer.

Step 1 — basic records with dig

dig example.com
dig +short A example.com
dig +short AAAA example.com
dig +short MX example.com
dig +short NS example.com
dig +short TXT example.com
dig +short SOA example.com

The default dig example.com queries an A record and prints the full response: status, flags, question, answer, authority and additional sections. +short reduces the answer to the record data, which is useful in scripts but hides status and authority information.

Step 2 — ask a specific server

# Query a specific recursive resolver
dig @1.1.1.1 example.com A

# Query an authoritative name server directly
dig @ns1.example.com example.com A +norecurse

@server sends the query to that server. +norecurse asks the server not to recurse, which is appropriate when querying an authoritative server. Do not use a public resolver for queries you are not authorized to make at volume.

Step 3 — reverse lookups

dig +short -x 192.0.2.10
dig +short PTR 10.2.0.192.in-addr.arpa

-x builds the reverse in-addr.arpa or ip6.arpa name for you. Reverse records are often missing or generic; a PTR does not prove ownership or identity.

Step 4 — inspect delegation

dig +trace example.com NS

+trace starts at the root and follows referrals to the authoritative servers. It is useful for understanding delegation problems, but it sends queries to multiple public servers and can be slower than a normal lookup.

Step 5 — registration data with whois

whois example.com
whois 192.0.2.10

# Query IANA and follow the referral chain explicitly
whois -I example.com

whois queries the registry or registrar responsible for the object. Output formats vary widely by registry. -I first queries whois.iana.org and follows its referral. Privacy services often replace registrant details; that is a normal result, not a failure.

What to record

RecordQuestion it helps answerCaution
A / AAAAWhich addresses does the name resolve to?CDNs and load balancers return changing or shared addresses
MXWhere does mail for the domain go?Third-party mail providers may be present
NSWhich servers are authoritative?Delegation can differ from parent records during transitions
TXTWhat verification or policy records exist?TXT is often used for SPF, DKIM, DMARC and ownership proofs
SOAWho is the primary authority and what are the timers?Serial numbers are not a security indicator
PTRWhat name is associated with an address?Frequently generic or stale
whoisWho is responsible for the registration or address block?Privacy redaction is common; dates and status matter

Limitations and interpretation

  • DNS answers can be cached. Use +noall +answer or query authoritative servers when freshness matters.
  • CDN addresses do not identify the origin server. Do not treat a shared address as dedicated infrastructure.
  • Wildcard DNS can make random subdomains appear to exist. Check whether a nonexistent name returns the same records.
  • Zone transfers (AXFR) are rarely allowed and usually require explicit authorization. Do not attempt them outside a scoped test.
  • WHOIS output is not a vulnerability finding. Registration data can be outdated or redacted.

Structured output

# Answer-only records for a report
dig +noall +answer example.com A
dig +noall +answer example.com MX
dig +noall +answer example.com TXT

# Save raw output
dig example.com ANY > ~/engagements/lab-2026-10-29/raw/dig-any.txt
whois example.com > ~/engagements/lab-2026-10-29/raw/whois-example.com.txt

Some resolvers refuse or minimize ANY queries. Prefer specific record types. See Working with results.

Troubleshooting

SymptomLikely causeWhat to check
status: NXDOMAINName does not exist in that zoneCheck spelling, search domain and the authoritative server
status: SERVFAILResolver or authoritative failureTry another resolver, then query the authoritative NS directly
No answer sectionRecord type absent, refused, or minimizedTry a different type and inspect the full response
dig: command not foundDNS group not installedRun eergn-recon-installer -t dns
whois returns no matchWrong registry, redaction or unsupported objectTry whois -I and the correct registry for the TLD

Security considerations

  • DNS queries reveal your resolver and can be logged. Use infrastructure appropriate to the engagement.
  • Subdomain brute force and high-volume enumeration are not covered here and require explicit scope and rate limits.
  • WHOIS data may contain personal information. Handle and retain it according to your engagement rules and privacy obligations.
