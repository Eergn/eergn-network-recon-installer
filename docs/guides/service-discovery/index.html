Service discovery

Move from "this host is up" to "these TCP or UDP services are exposed". The guide uses Nmap for structured discovery and Netcat for a small, targeted reachability check.

Purpose

Identify listening services on authorized hosts, capture the evidence, and decide what needs a closer, human review. A version banner is not proof of a vulnerability. It is a clue that needs confirmation against the actual service and version.

Prerequisites

  • A confirmed host list and explicit authorization for the ports and time window.
  • Installed groups nmap and netcat.
  • An agreement on scan intensity. Start small and increase only if the scope allows it.

Step 1 — start with a bounded scan

# Scan the 100 most common TCP ports on one authorized host
nmap -sV -T3 --top-ports 100 192.168.1.10

# Or a specific list of ports
nmap -sV -T3 -p 22,25,53,80,443,8080 192.168.1.10

-sV probes open ports to identify service and version. -T3 is Nmap's normal timing template. --top-ports 100 limits the port set, which keeps the first pass small. The default SYN scan requires raw-socket privileges; without them, Nmap may fall back or you can request a TCP connect scan explicitly with -sT.

Port scans are active

Every probe reaches the target and can be logged, rate-limited or blocked. Do not scan public systems or ranges outside your scope. Avoid aggressive timing (-T4/-T5) unless the scope explicitly allows it and the target can tolerate it.

Step 2 — separate open ports from the noise

nmap -sV -T3 --open -p 1-1024 --reason 192.168.1.10

--open shows only open, open|filtered and unfiltered ports. --reason explains why Nmap assigned each state. A state of filtered usually means a firewall or packet filter dropped the probe; it does not prove the port is closed.

Step 3 — confirm a single reachable service with Netcat

Netcat is useful for a narrow check: "can I establish a TCP connection to this host and port?" It is not a substitute for a port scan.

# Zero-I/O TCP check with a short timeout
nc -zv -w 3 192.168.1.10 443

-z sends no application data, -v prints a result and -w 3 bounds the connection attempt. A successful TCP handshake does not guarantee the application is healthy; it only confirms that something accepted the connection.

Step 4 — inspect a service banner carefully

If the scope allows interaction with a service, a simple banner or HTTP response can confirm what is listening:

# Read an HTTP response header without downloading a full page
curl -sS -I --max-time 5 http://192.168.1.10/

# Read an SMTP greeting, then close the connection
nc -w 3 192.168.1.10 25

These commands send application data and may appear in service logs. Use them only on services you are authorized to interact with. Do not use banner grabbing on third-party systems.

Step 5 — save the evidence

mkdir -p ~/engagements/lab-2026-10-29/raw
nmap -sV -T3 --open -p 22,80,443,8080 -oA ~/engagements/lab-2026-10-29/raw/services-192.168.1.10 192.168.1.10

-oA writes normal, XML and grepable formats. The XML is useful for later parsing; the normal report is readable. Treat both as sensitive.

Reading Nmap port states

StateMeaningPractical interpretation
openA service accepted the probeInvestigate the service and its version
closedThe host responded but no service is listeningPort is reachable at the network layer
filteredNo response, or a filter dropped the probeFirewall or packet filter; do not assume closed
unfilteredPort is reachable but state is undeterminedOften used with ACK scans
open|filteredCannot distinguish open from filteredCommon for UDP scans; needs a different probe

Interpreting version detection

  • -sV matches probes against service fingerprints. It can be wrong or approximate, especially behind proxies, load balancers or custom daemons.
  • A version string is not a vulnerability assessment. Verify the actual software version through an authorized management interface before drawing conclusions.
  • Services can share ports: HTTP on 8080, TLS on 8443, SSH on nonstandard ports. Do not assume a service from the port number alone.
  • UDP services need -sU and are slower and less reliable. Add UDP only for explicitly scoped ports.

Advanced: controlled default scripts

Nmap's default scripts can add useful service detail, but they are active and may be intrusive. Use them only when the scope allows script scanning:

nmap -sV -sC -T3 -p 22,80,443 192.168.1.10

-sC is equivalent to --script=default. Review the Nmap script documentation before running categories against production or fragile services.

Troubleshooting

SymptomWhat to check
All ports filteredHost firewall, network ACL, wrong host, or scan blocked; test a known open port and check routing
-sV shows tcpwrappedACL or service wrapper accepted and immediately closed; confirm with the service owner
Nmap says it needs rootUse sudo for SYN scanning or choose -sT for a connect scan
Netcat hangsAdd -w; the service may not speak first, or a firewall is silently dropping traffic
Results differ between runsLoad balancing, dynamic firewalls, rate limiting or service restarts; record timing

Security considerations

  • Scanning creates logs and can trigger defenses. Confirm monitoring expectations before a production assessment.
  • Rate-limit when possible. Nmap's timing templates affect probe volume; -T3 is a conservative default.
  • Do not use stealth or evasion options to bypass controls you are not authorized to test.
  • Service banners may contain internal hostnames, software versions or other sensitive information. Protect the output.
