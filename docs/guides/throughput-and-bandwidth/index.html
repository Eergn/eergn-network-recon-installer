Throughput and bandwidth

Measure what a link can carry with iperf3, then attribute live traffic to connections or processes with iftop and nethogs. These tools answer different questions and should not be used interchangeably.

Purpose

  • iperf3 measures achievable throughput between two endpoints you control.
  • iftop shows live bandwidth by host/connection on an interface.
  • nethogs shows live bandwidth by process.

None of these tools is a discovery or vulnerability scanner. They observe or generate traffic for performance work.

Prerequisites

  • Installed groups iperf3 and bandwidth.
  • Two endpoints you control for iperf3: a server and a client.
  • Root or sudo for packet capture in iftop and nethogs, and permission to open the iperf3 port (default 5201).
  • A maintenance window if the test could saturate a production link.

Step 1 — start an iperf3 server

On the server endpoint:

iperf3 -s

The server listens on TCP port 5201 by default and waits for a client. The command stays in the foreground; use a separate terminal or a service manager for longer tests. Open the port in the host firewall only for the client addresses that need it.

For a single test then exit:

iperf3 -s -1

Step 2 — run a bounded client test

# 10-second TCP test
iperf3 -c 192.168.1.20 -t 10

# Four parallel streams
iperf3 -c 192.168.1.20 -t 10 -P 4

# Reverse direction: server sends, client receives
iperf3 -c 192.168.1.20 -t 10 -R

-t 10 limits the test to ten seconds. -P 4 runs four parallel streams, which can reveal whether a single stream is limited by latency or window size. -R reverses the direction. Compare both directions, because asymmetric links and shaping are common.

Step 3 — UDP or bidirectional tests (when appropriate)

# UDP at a target bitrate
iperf3 -c 192.168.1.20 -u -b 100M -t 10

# Bidirectional TCP
iperf3 -c 192.168.1.20 --bidir -t 10

-u switches to UDP. -b 100M sets the target bitrate; without a target, UDP behavior can be unintended. UDP results include loss and jitter, not just throughput. --bidir is supported by the installed iperf3 3.20 help output; older versions may not accept it.

Step 4 — save machine-readable results

iperf3 -c 192.168.1.20 -t 10 -J > ~/engagements/lab-2026-10-29/raw/iperf3-tcp.json
iperf3 -c 192.168.1.20 -t 10 -R -J > ~/engagements/lab-2026-10-29/raw/iperf3-reverse.json

-J produces JSON. The schema is version-dependent; record the iperf3 version alongside the results.

Step 5 — attribute live traffic with iftop

# Per-connection view, no DNS/service lookups
sudo iftop -i eth0 -n -N -P

# Text mode, one 10-second sample, then exit
sudo iftop -i eth0 -n -N -P -t -s 10

-i selects the interface. -n disables hostname lookups and -N disables service-name lookups, which keeps the display fast and avoids extra DNS traffic. -P shows ports. -t uses the text interface; -s 10 prints one sample after ten seconds and exits.

Step 6 — attribute live traffic to processes with nethogs

# Monitor the default interfaces
sudo nethogs

# Two-second refresh on a specific interface
sudo nethogs -d 2 eth0

# Trace mode for scripted output
sudo nethogs -t eth0

-d sets the refresh interval in seconds. -t enables trace mode, which is more suitable for logging than the interactive display. nethogs is Linux-focused; the README notes that it may be unavailable or fail on macOS.

Interpreting the numbers

ToolUnits / viewWhat it tells youLimitations
iperf3bits/sec by default; -f changes formatAchievable throughput between two controlled endpointsSynthetic traffic; does not reflect real application mix
iftopbits/sec by default; -B for bytesLive traffic by host/connectionSnapshot of the interface; hostname attribution can be noisy
nethogskB/s or totals depending on view modeLive traffic by processLinux-focused; process attribution can be incomplete for some traffic

Do not compare iperf3 results directly with iftop's instantaneous rate and call one of them wrong. iperf3 reports a controlled test over a window; iftop and nethogs report live traffic with different sampling and aggregation. Record the interface, time window and direction for every measurement.

Troubleshooting

SymptomWhat to check
iperf3 cannot connectServer running, port 5201 reachable, firewall, correct address, not a captive network
the server is busy running a testAnother client is using the server; wait or use -1 for one-off mode
Throughput much lower than link speedDuplex mismatch, shaping, latency/window size, parallel streams, CPU limits
iftop shows no trafficWrong interface, promiscuous mode not needed for own traffic, permissions
nethogs cannot open interfacesRun with sudo; check the device name and kernel support

Security considerations

  • An iperf3 test can saturate a link. Schedule it and agree on limits with the network owner.
  • iftop and nethogs capture packet metadata. Treat captured hostnames, addresses and process names as sensitive.
  • Do not run promiscuous-mode captures on networks you do not own; you may observe other people's traffic.
  • Use -1 or stop the iperf3 server after the test to avoid leaving a service listening.
