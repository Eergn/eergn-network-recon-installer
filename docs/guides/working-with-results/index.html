Working with results

Reconnaissance output is evidence. Save it consistently, record the context, compare runs, and protect it like any other sensitive assessment artifact.

Purpose

Make results reproducible and reviewable. The installer does not provide a reporting engine, database or dashboard. This guide uses the output features of the upstream tools plus ordinary files, directories and shell tools.

Prerequisites

  • Installed tools relevant to the data you are collecting.
  • A directory convention you can explain to a reviewer.
  • An agreed retention and handling policy for sensitive data.

Suggested directory layout

~/engagements/
  lab-2026-10-29/
    scope.txt
    notes.md
    raw/
      arp-scan.txt
      fping-alive.txt
      nmap-ping.nmap
      nmap-ping.xml
      services-192.168.1.10.nmap
      tls-lab.json
      iperf3-tcp.json
    processed/
    reports/

Keep raw output immutable. Write summaries and derived files elsewhere so you can always return to the original. Put the scope, authorization reference and time window in scope.txt.

Saving output by tool

ToolUseful output optionNotes
Nmap-oN, -oX, -oG, -oA <base>-oA writes normal, XML and grepable formats together
dig> file or +noall +answerShell redirection captures the full response; +short is for scripts
testssl.sh--jsonfile, --htmlfile, --logfileJSON/HTML are additional outputs; check the version's schema
iperf3-JJSON schema is version-dependent; record the iperf3 version
mtr-r, -w, -jReport mode is better for records than the live curses view
arp-scan--plain, --formatPlain output is easier to parse; fields are documented in arp-scan's help
installerLog path printed at startTemporary log; copy it into the engagement directory if needed

Record context with the result

A result without context is hard to defend later. Capture at least:

  • Date, start and end time, and timezone.
  • Source host, interface and source address.
  • Target scope and excluded addresses.
  • Exact command line, including options and tool version.
  • Authorization reference or change ticket.
  • Unexpected conditions: rate limiting, outages, maintenance windows.
{
  echo "date: $(date -Is)"
  echo "host: $(hostname)"
  echo "command: nmap -sV -T3 --open -p 22,80,443 192.168.1.10"
  nmap --version | head -n 1
} > ~/engagements/lab-2026-10-29/raw/services-192.168.1.10.meta

Storing the command and version alongside the output prevents the classic "which flags produced this file?" problem.

Comparing runs

diff -u raw/services-192.168.1.10.nmap raw/services-192.168.1.10.after.nmap
diff -u raw/fping-alive.txt raw/fping-alive.after.txt

diff -u is usually enough for text reports. For XML, parse with a tool you already trust rather than comparing lines. Keep the baseline and the new run so the difference is explainable.

Filtering without destroying the source

# Show only open-port lines from a normal Nmap report
grep -E "open|filtered" raw/services-192.168.1.10.nmap

# Answer records only
dig +noall +answer example.com A > processed/dns-a.txt

Write filters to new files. Do not edit the raw evidence in place. If a filter is part of the methodology, record the filter in your notes.

Protecting sensitive output

  • Host inventories, service banners and certificate details can expose internal architecture.
  • WHOIS records may contain personal data; handle them according to privacy and engagement rules.
  • Use restrictive directory permissions and your organization's approved encryption for data at rest.
  • Do not paste raw results into public issues, chat or documentation without scrubbing addresses, names and certificates.
chmod 700 ~/engagements/lab-2026-10-29
chmod 600 ~/engagements/lab-2026-10-29/raw/*
No built-in reporting

The installer and its supported tools do not provide a case-management, database or report-generation feature. Any automation you build around them is your own; do not assume the project stores or transmits results.

Retention and disposal

Follow the engagement's retention policy. When data is no longer needed, remove it in a way that matches its sensitivity and your organization's requirements. Do not leave raw scan output in world-readable temporary directories.

Troubleshooting

ProblemWhat to check
File is emptyCommand failed before writing; check stderr and the exit status
Output looks truncatedResource limits, interrupted scan or a full disk; check the tool's log
Timestamps are confusingRecord timezone explicitly; use date -Is
Sensitive file was sharedFollow the incident process; rotate anything exposed and review the content

Security considerations

Results are often more sensitive than the scan itself. A host inventory can be more useful to an attacker than a list of open ports. Protect the data, limit access and retain only what the engagement requires.
