Host discovery in an authorized lab

Build a defensible inventory of hosts on a network you own. The guide combines Layer-2 ARP discovery, ICMP reachability and Nmap host discovery, and explains why the three views disagree.

Purpose

Answer a narrow question: which hosts are present on this authorized segment or range? Host discovery is not service discovery. It does not tell you which ports are open, what software is running, or whether a host is vulnerable.

Prerequisites

  • Written scope covering the exact interface, subnet and time window.
  • Root or sudo for arp-scan (raw sockets) and usually for Nmap's default SYN-based discovery.
  • Installed groups arp-scan, fping and nmap.
  • A private lab network. The examples use 192.168.1.0/24; replace it with your authorized scope.

Required tools

arp-scan, fping and Nmap. Install them with:

sudo eergn-recon-installer -t arp-scan -t fping -t nmap -y

Step 1 — confirm the interface and route

ip -brief address
ip route

Write down the interface connected to the lab and its prefix. Do not assume the default route points at the lab. If you have multiple interfaces, select the correct one explicitly in the next steps.

Step 2 — discover local IPv4 neighbors with ARP

arp-scan sends ARP requests on the local Layer-2 segment. It is normally the most reliable way to find hosts on the same broadcast domain because ARP is not usually filtered the way ICMP is.

# Use the interface that faces the lab
sudo arp-scan --interface=eth0 --localnet

--localnet derives the target range from the interface address and netmask. --interface prevents arp-scan from silently choosing a different interface. If you omit it, arp-scan chooses the lowest-numbered configured up interface, which may not be the one you intend.

For a script-friendly list of IP and MAC addresses:

sudo arp-scan --interface=eth0 --localnet --plain --format='${ip}\t${mac}\t${vendor}'
Layer-2 boundary

ARP does not cross routers. If the lab spans multiple VLANs or subnets, arp-scan --localnet only sees the local broadcast domain. Use a reachability tool for routed ranges.

Step 3 — check routed reachability with fping

fping sends ICMP echo requests quickly and can enumerate a CIDR range. It shows only hosts that answer ICMP, so a host that blocks ICMP can still be up.

# Show hosts that respond
fping -a -g 192.168.1.0/24 2>/dev/null

# Send three probes per host and include statistics
fping -c 3 -s -g 192.168.1.0/24 2>/dev/null

-a prints alive targets only. -g generates the target list from the CIDR range. Redirecting stderr hides the per-probe "unreachable" noise, which is useful for a clean list but means you should re-run without it when debugging.

Step 4 — cross-check with Nmap host discovery

Nmap's ping scan -sn performs host discovery without a port scan. It may use several probe types depending on privilege and target.

nmap -sn 192.168.1.0/24

# Save a grepable and normal report for later comparison
nmap -sn -oN lab-ping.nmap -oG lab-ping.gnmap 192.168.1.0/24

On a local Ethernet, Nmap may use ARP for hosts on the same subnet. For routed targets it uses ICMP, TCP and other probes depending on options and privileges. Use --reason to see why a host was considered up:

nmap -sn --reason 192.168.1.0/24

Step 5 — compare the three views

ToolWhat it seesTypical blind spot
arp-scanHosts that answer ARP on the local Layer-2 segmentAnything behind a router; hosts with unusual ARP filtering
fpingHosts that answer ICMP echo requestsHosts or firewalls that drop ICMP
Nmap -snHosts that answer Nmap's discovery probes, including ARP on local subnetsSilently filtered hosts without -Pn; -Pn then skips discovery entirely

Do not "fix" a missing host by blindly adding -Pn. -Pn treats every target as online and skips discovery, which is appropriate when you have a known target list but not when you are trying to inventory a range. If a host is missing from all three views, verify link, VLAN, firewall and local ARP behavior before assuming it is absent.

Step 6 — record the result

mkdir -p ~/engagements/lab-2026-10-29/raw
sudo arp-scan --interface=eth0 --localnet --plain > ~/engagements/lab-2026-10-29/raw/arp-scan.txt
fping -a -g 192.168.1.0/24 2>/dev/null | tee ~/engagements/lab-2026-10-29/raw/fping-alive.txt
nmap -sn -oA ~/engagements/lab-2026-10-29/raw/nmap-ping 192.168.1.0/24

-oA writes normal, XML and grepable output with one basename. See Working with results for storage and comparison practices.

Troubleshooting

SymptomLikely causeWhat to check
arp-scan: command not foundThe group is not installedRun eergn-recon-installer --check, then install -t arp-scan
arp-scan: Permission denied or no responsesRaw socket privileges missing or wrong interfaceUse sudo, confirm --interface, and verify the link is up
fping reports every host unreachableICMP blocked, wrong range or no routeTry a known host, check ip route, and inspect the unfiltered fping output
Nmap misses a host that ARP seesNmap discovery probe filtered or target behind a routerUse --reason; for a known host, -Pn is appropriate
ARP shows duplicate addressesDuplicate IP, proxy ARP or a moving VMInvestigate the MAC and switch port; do not treat it as a scan error

Security and scope

  • ARP requests reveal your interface and MAC to the local segment. This is normal local traffic, not stealthy reconnaissance.
  • ICMP and Nmap probes can trigger IDS/IPS or network monitoring alerts.
  • Do not run --localnet on a segment outside your authorization because it enumerates whatever the interface can reach at Layer 2.
  • Host inventories can expose device names, MAC vendors and internal addressing. Store them as sensitive assessment data.

Continue with Service discovery once the host inventory is understood.
