Contributing

How to change the installer, add a tool group, update the package or improve the documentation without breaking the APT repository or the static site.

Before you start

Inspect the current source and open an issue describing the change. The repository has no CONTRIBUTING.md, test suite or CI configuration in the audited tree, so these conventions are derived from the actual scripts and README rather than from a formal policy.

git clone https://github.com/Eergn/eergn-network-recon-installer.git
cd eergn-network-recon-installer
bash -n eergn-recon-installer.sh
./eergn-recon-installer.sh --list

Add a tool group

A group is defined by four functions in eergn-recon-installer.sh. Update all of them together:

  1. ALL_IDS — add the new ID in the menu order.
  2. tool_desc — add the human-readable label.
  3. tool_cmds — list every command that must exist for the group to count as installed.
  4. pkgs_for — add the package name for each supported package manager key: apt, dnf, pacman, zypper, apk and brew.

If the tool needs special handling, follow the tls pattern: install the normal packages, then call a dedicated function such as ensure_testssl. Add fallback logic only when you can explain its failure behavior and security implications.

Package names are platform-specific

Do not add a package that does not exist for a supported manager. If a tool is unavailable on one platform, decide explicitly whether the group should fail there and document it. The README already notes that nethogs is Linux-focused.

Add or change a package manager

Update detect_pm for detection, pm_install for the install command, pkgs_for for every group mapping, and refresh_index if the manager needs an explicit refresh. Also update the README platform table and the command reference.

Update the version

The version is read from VERSION="..." in the installer by scripts/build-deb.sh. When changing it, also update the man page generation if necessary, the README examples that mention 1.0.0, the published .deb, docs/Packages, Release and signatures. Do not hand-edit repository indexes; rebuild them with the script.

Build and verify

# Syntax and non-destructive checks
bash -n eergn-recon-installer.sh
./eergn-recon-installer.sh --list
./eergn-recon-installer.sh --check
./eergn-recon-installer.sh --all --dry-run --no-banner

# Package build (requires dpkg-deb from dpkg-dev)
./scripts/build-deb.sh
dpkg-deb -I dist/eergn-recon-installer_1.0.0_all.deb

# APT repository refresh (maintainer machine, requires gnupg and dpkg-dev)
./scripts/make-apt-repo.sh

These checks were run while preparing this documentation where the required tools were available; they are not a substitute for testing on each supported distribution. Do not claim a platform works unless you have actually exercised it. If you add a tool, test the dry run and the real installation on at least one package manager.

Documentation conventions

  • Pages are static HTML under docs/ with relative links so the GitHub Pages project subpath keeps working.
  • Each docs page contains its own header, sidebar and footer. When adding a page, copy an existing page at the same depth, update the title, description, breadcrumbs, active sidebar link and previous/next navigation in the neighboring pages.
  • Add the page to docs/assets/js/search-index.js with a title, path relative to docs/, category, description and keywords.
  • Use the existing CSS components: .callout, .table-scroll, .tool-meta and standard .prose elements. Avoid adding a framework for a small interaction.
  • Verify commands against official upstream documentation or installed help output. Label environment-specific or unverified behavior clearly.
  • Do not publish real scan results, internal addresses, personal registration data or credentials.

Links and attribution

Prefer official upstream sites and repositories over third-party tutorials. Do not imply that an upstream project endorses this installer. Preserve license and copyright notices when redistributing tool output or documentation.

Security-related contributions

Be cautious with changes that affect privilege handling, repository signing, downloaded code or the testssl.sh fallback. Explain the threat model and failure mode in the pull request. Do not weaken signature verification or add broad permission changes to work around a local problem.

What not to commit

  • Build output in dist/ or root-level .deb files; they are ignored.
  • Private signing keys, passphrases or tokens.
  • Real assessment data, internal hostnames or customer information.
  • Generated temporary logs or editor backup files.

Pull request checklist

  • Installer syntax passes bash -n.
  • --list, --check and --all --dry-run behave as expected.
  • Every new group has mappings for every supported package manager, or an explicit documented limitation.
  • README, command reference and tool catalog are updated.
  • Internal links and assets work at the project subpath.
  • No secrets, personal data or unverified claims are included.
