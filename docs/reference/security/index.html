Security and responsible use

Reconnaissance tools generate traffic that looks like scanning. This page covers authorization, repository trust, privilege boundaries, data sensitivity and the specific risks of each installed tool.

Authorization comes first

The installer grants no permission to test anything. Use these tools only on networks and systems you own or have explicit, recorded authorization to assess. "Publicly reachable" is not authorization.

Active versus passive

Most tools in this collection actively send traffic. Only whois and ordinary DNS lookups are close to passive, and even those reach third-party services.

Scope and rate limits

  • Define hosts, ports, protocols, time window and excluded systems before starting.
  • Prefer the least intrusive probe that answers the question. A single dig +short is not a full scan.
  • Use conservative timing (-T3 in Nmap) and bound test durations.
  • Watch for rate limiting and retries; a scan that evades a rate limit is not necessarily authorized.
  • Do not use stealth, decoy or evasion options to bypass controls outside an explicitly authorized test.

Repository and supply-chain trust

The APT repository is served over HTTPS from GitHub Pages and signed with an Ed25519 key. The published fingerprint is:

900D437EB8F512053DA25632AEF17B55E71A8350

Trusting a key fetched in the same command as the source definition protects transport integrity, not publisher identity. Compare the fingerprint through a second channel you trust before adding the key to /usr/share/keyrings.

  • The signing key has no expiration field in the published key. That reduces operational expiry friction but means revocation and key rotation are procedural.
  • The APT package installs only the installer script, docs and man page, and depends on bash. The external tools come from your distribution's repositories.
  • On the RHEL family, the installer may rely on EPEL for arp-scan, iftop and nethogs. Enabling EPEL is a separate trust decision.
  • The testssl.sh fallback performs a shallow clone of the upstream default branch into /opt/testssl.sh. It does not pin a commit or verify a checksum. If you require reproducibility, install testssl.sh through your distribution or pin the upstream commit yourself and audit the script.

Privileges

  • The installer needs root or sudo to install packages. It uses sudo only for package-manager operations.
  • On macOS it refuses to run as root because Homebrew manages its own prefixes.
  • arp-scan, iftop and nethogs need packet-capture or raw-socket privileges. Prefer capabilities or targeted sudo over running a whole workflow as root.
  • Do not fix permission errors by recursively changing ownership or permissions of system directories.

Sensitive output

Reconnaissance output can expose internal addressing, service versions, certificate details and registration data. Treat results as sensitive assessment records: restrictive permissions, approved encryption at rest, limited sharing and a defined retention period. See Working with results.

Tool-specific notes

  • Nmap: version detection and scripts send additional probes; -sC can be intrusive on fragile services.
  • Netcat/Ncat: listeners can expose a shell if combined with -e/--exec. Never bind an exec listener to an untrusted interface.
  • arp-scan: local-segment only; running it on the wrong interface can enumerate a network outside your scope.
  • fping/MTR: ICMP or TCP/UDP probes can trigger monitoring and may be blocked.
  • dig: high-volume enumeration and zone transfers require explicit authorization and rate control.
  • whois: results may contain personal data; handle according to privacy obligations.
  • OpenSSL/testssl.sh: testssl.sh opens many connections and can be noisy; do not run it against third-party endpoints without permission.
  • iperf3: can saturate links; schedule tests and stop the server afterwards.
  • iftop/nethogs: promiscuous mode can capture other users' traffic metadata; use only on networks you control.
